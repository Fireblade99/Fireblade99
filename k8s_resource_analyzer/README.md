# k8s-resource-analyzer

Ищет поды, которые запрашивают ресурсы (CPU и память) сильно больше, чем используют, и поды, которым ресурсов не хватает. Данные берёт из VictoriaMetrics/Prometheus: метрики cAdvisor и kube-state-metrics. Основной сценарий — неймспейс Airflow (`mpa-airflow-6679`), где каждый запуск задачи является отдельным подом.

## Что в отчёте

| Лист | Содержимое |
|---|---|
| **Summary** | Сколько workload'ов с перерасходом и с нехваткой. Сколько ресурса запрошено за неделю (`request × время`) и какая доля простаивала. Топ-10 по перерасходу памяти и топ-10 по **простаивающему резерву** в GiB·ч |
| **Recommendations** | Одна строка на workload (DAG/task или имя пода без случайного суффикса): число запусков, request, средняя и пиковая нагрузка, рекомендация (`пик × 1.2`), waste, простаивающий резерв, OOM, статус |
| **Runs** | **Одна строка на каждый запуск** (под) за неделю: DAG, task, run_id, try, старт и конец, длительность, request и limit, средняя и пиковая фактическая нагрузка, **превышение request над пиком** (абсолютное и в %), простаивающий резерв, OOMKilled. Числа хранятся как числа, поэтому лист можно сортировать и фильтровать |

Термины:
- **Over-request** = `request − пик` за запуск. Это то, сколько разработчик запросил сверх фактического пика. Отрицательное значение означает, что под использовал больше, чем запросил (риск троттлинга или OOM).
- **Idle GiB·ч / core·ч** = `(request − среднее) × длительность`. Это ресурс, который был зарезервирован на ноде и простаивал. Учитывает и частоту запусков, и их длительность: задача с запросом 512Gi, которая идёт 10 минут раз в сутки, весит меньше, чем 100Gi, которые простаивают круглосуточно.

## Нагрузка на VictoriaMetrics

- Неделя запрашивается **кусками по 24 часа** (`chunk_hours`), куски идут последовательно с паузой (`pause_seconds`).
- Агрегация выполняется на стороне VM (`max by (namespace, pod, container)`), поэтому назад приходит один ряд на контейнер.
- Subquery не используются.
- Requests, limits, лейблы и OOM берутся мгновенными запросами `max_over_time(...[24h])`, тоже по одному на кусок.
- Итого за неделю около 40 HTTP-запросов. Если VM всё равно тяжело, уменьшите `--chunk-hours` (например, до 6) и увеличьте `--pause`.

## Запуск (Windows, PowerShell)

```powershell
cd k8s_resource_analyzer
py -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy config.example.yaml config.yaml

# 1. Проверить, что VM доступна и какие метрики и лейблы в ней есть
python main.py -c config.yaml --check

# 2. Отчёт за неделю
python main.py -c config.yaml -o excel
```

Полезные флаги:

| Флаг | Что делает |
|---|---|
| `--no-k8s` | Не обращаться к Kubernetes API (kubeconfig не нужен), requests брать из kube-state-metrics. В `config.example.yaml` это поведение уже выбрано: `kubernetes.enabled: false` |
| `--all` | Показывать все workload'ы, а не только проблемные |
| `--step 1m` | Более точная длительность коротких задач (запросы тяжелее) |
| `--chunk-hours 6 --pause 3` | Ещё мягче для VM |
| `--use-proxy` | Ходить в VM через `HTTP(S)_PROXY`. По умолчанию прокси **игнорируется**, потому что корпоративный прокси обычно не видит внутренние адреса кластера |
| `--lookback-days 3` | Глубина анализа |

## Ограничения

- **Колонки DAG / Task / Run ID** заполняются, только если kube-state-metrics отдаёт лейблы подов Airflow (`--metric-labels-allowlist=pods=[dag_id,task_id,run_id,try_number]`). `--check` показывает, есть ли они. Без лейблов группировка идёт по имени пода без случайного суффикса, как раньше.
- Время старта и конца запуска определяется с точностью до шага (`step`, по умолчанию 5 минут). Пик при этом не теряется: `max_over_time` и `rate` берутся по окну шага.
- Задача, которая прожила меньше одного scrape-интервала, может не попасть в метрики cAdvisor.
