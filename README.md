# Мониторинг удалённого PostgreSQL

Хелсчек, время отклика, насыщение и здоровье данных — в вашей Grafana.

## Как это устроено

```
    ХОСТ БАЗЫ ДАННЫХ                    ВАША МАШИНА (Windows)
 ┌────────────────────────┐          ┌──────────────────────────────┐
 │  PostgreSQL            │          │                              │
 │       ▲                │          │   pg-probe          :9899    │
 │       │ localhost      │          │     │  время отклика по сети │
 │  postgres_exporter     │◀─────────┼─────┤  + 4 метрики, которых  │
 │                 :9187  │  scrape  │     │    нет в экспортёре    │
 │                        │          │     ▼                        │
 │  node_exporter  :9100  │◀─────────┼──▶ Prometheus       :9090    │
 │    диск, CPU, память   │  scrape  │          │                   │
 └────────────────────────┘          │          ▼                   │
      уже стоит у админов            │      Grafana (ваша)          │
                                     └──────────────────────────────┘
```

Два независимых наблюдателя — это не избыточность, а диагностика.
Экспортёр смотрит на базу изнутри хоста, пробер — снаружи, тем же
путём, которым ходит приложение. Их расхождение сразу называет причину:

| `pg_up` | `pgprobe_up` | Диагноз |
|---|---|---|
| 0 | 0 | лежит сама база |
| 1 | 0 | база жива, **проблема в сети** между вами и ней |
| нет | 0 | лежит весь хост целиком |

Пробер стоит на вашей стороне намеренно. Мониторинг, который живёт на
том же хосте, что и база, теряет вместе с ним ровно ту историю, ради
которой он и нужен.

## Что ставить

На хосте БД — **ничего**: `postgres_exporter` и `node_exporter` там уже
работают.

На вашей машине:

```powershell
# PowerShell от имени администратора
.\windows\Install-PgProbe.ps1 `
    -PgHost db.example.com `
    -PgPassword 'пароль роли monitoring' `
    -DbHostAddress db.example.com `
    -WithPrometheus
```

`-WithPrometheus` опущен, если Prometheus у вас уже есть — тогда
добавьте к себе блоки `scrape_configs` и `rule_files` из
[`prometheus/prometheus.yml`](prometheus/prometheus.yml).

Дальше:

1. В Grafana добавить источник данных Prometheus.
2. Импортировать [`grafana/postgres-dashboard.json`](grafana/postgres-dashboard.json).
3. Алерты подключить к своему каналу уведомлений — условия готовы в
   [`prometheus/rules/postgres.alerts.yml`](prometheus/rules/postgres.alerts.yml),
   осталось привязать Alertmanager или Grafana Alerting.

### Роль в базе

Проберу нужна учётка. Суперюзер не нужен — хватает встроенной роли
`pg_monitor`, которая даёт доступ к статистике, но не к данным:

```bash
psql "$SUPERUSER_DSN" -v mon_password="'ПАРОЛЬ'" -f sql/01_monitoring_role.sql
psql "$SUPERUSER_DSN" -f sql/02_monitoring_schema.sql   # только для медленных запросов
psql "postgresql://monitoring:ПАРОЛЬ@host/db" -f sql/99_verify.sql   # все строки должны быть OK
```

Роли выставлены `statement_timeout`, `lock_timeout` и
`idle_in_transaction_session_timeout`: мониторинг ни при каких
обстоятельствах не должен блокировать рабочую нагрузку. Если его запрос
ждёт лок дольше 5 секунд — падает он, а не база.

## Первым делом: проверить совместимость

Имена метрик в `postgres_exporter` менялись между версиями. Экспортёр
на хосте ставили не вы и версию не выбирали, поэтому прежде чем верить
алертам:

```bash
python3 tools/check_targets.py \
    --postgres-exporter http://db-host:9187/metrics \
    --node-exporter     http://db-host:9100/metrics \
    --probe             http://127.0.0.1:9899/metrics
```

Скрипт вытаскивает из правил все метрики, на которые они ссылаются, и
сверяет с тем, что реально отдают эндпоинты. **Метрика, которой нет, не
роняет Prometheus — правило просто молча никогда не срабатывает.** Это
худший вид поломки мониторинга, и ловится он только такой проверкой.

## Что меряется

### Время отклика — разложенное на слои

Обычный хелсчек отвечает «жива/не жива». Этого мало: база чаще
деградирует, чем падает. Пробер разбивает задержку на четыре слоя, и по
тому, какой из них вырос, сразу видно, куда смотреть:

| Слой | Что включает | О чём говорит рост |
|---|---|---|
| `tcp_connect` | только сокет | сеть; Postgres ни при чём |
| `connect` | + TLS + авторизация | кончаются слоты, дорогой хендшейк, DNS |
| `ping` | `SELECT 1` по новому соединению | стоимость соединения целиком |
| `session_ping` | `SELECT 1` по готовому | **тормозит сам сервер** |

### Насыщение

Подключения по состояниям и в долях от `max_connections`, возраст самой
долгой транзакции, зависшие `idle in transaction`, заблокированные
сессии. Упереться в `max_connections` — самый частый способ уронить
прод: база остаётся «живой», а клиенты получают отказ, и обычный
хелсчек этого не замечает.

### Тихие убийцы

Здесь то, что копится месяцами и роняет базу разом:

* **Wraparound.** На 2 млрд транзакций Postgres останавливает приём
  записи. Не деградация — полная остановка, лечится долгим `VACUUM
  FREEZE` в оффлайне. Стоковый экспортёр эту метрику не отдаёт вообще.
* **Брошенный слот репликации.** Пока слот существует, Postgres обязан
  хранить весь WAL с его `restart_lsn`. Умерший потребитель молча съедает
  диск.
* **Свободное место на диске.** Изнутри Postgres не видно в принципе —
  только через `node_exporter`. Переполнение тома останавливает запись
  мгновенно, поэтому есть и предупреждение по тренду за сутки вперёд.
* **Автовакуум, который не справляется** — мёртвые строки, распухание,
  испорченные планы.

### Эффективность

Попадания в кэш, доля откатов, взаимоблокировки, временные файлы
(нехватка `work_mem`), досрочные чекпоинты (мал `max_wal_size`).

## Четыре метрики от пробера

Стоковый экспортёр закрывает почти всё, но четырёх вещей не отдаёт —
их снимает пробер, попутно, тем же соединением:

| Метрика | Почему её нет в экспортёре |
|---|---|
| `pgprobe_xid_age` | `age(datfrozenxid)` не собирается вовсе |
| `pgprobe_blocked_sessions` | `pg_locks_count` разбит по `mode`, но не по `granted` |
| `pgprobe_postmaster_uptime_seconds` | есть только аптайм самого экспортёра |
| `pgprobe_statement_*` | коллектор `pg_stat_statements` выключен по умолчанию |

Последняя строка требует `pg_stat_statements` в базе и прогнанного
`sql/02`. Нет — пропадёт только раздел медленных запросов, всё
остальное работает; пробер об этом предупредит один раз и не будет
сыпать ошибками.

## Проверка правил

```bash
promtool check rules prometheus/rules/*.yml
promtool test rules prometheus/tests/alerts_test.yml
promtool test rules prometheus/tests/vacuum_test.yml
python3 probe/test_classify.py
```

Тесты проверяют не только «алерт сработал», но и «НЕ сработал, когда не
должен». Ложные срабатывания приводят к тому, что алерты начинают
игнорировать, а это хуже их отсутствия. Два случая зафиксированы как
регрессии, потому что оба уже один раз были ошибкой:

* на **простаивающей** базе отношение попаданий в кэш не определено
  (`0/0`), а не равно нулю — иначе алерт «< 95%» будил бы каждую ночь;
* `last_autovacuum = 0` означает «никогда», а не «в 1970 году» — иначе
  алерт срабатывал бы на каждой новой таблице.

## Чего здесь нет

* **Логов Postgres.** Их не видно ни изнутри базы, ни через экспортёры.
  Если нужны — это отдельный сбор на хосте БД.
* **Надёжного алерта на слот, которым ни разу не пользовались.**
  Стоковая метрика отдаёт для него `NaN`. Опасный случай (слот работал,
  потом потребитель умер) отслеживается нормально, а последствия любого
  варианта ловит алерт на диск.
* **Разбора конкретных планов запросов.** Видно, какой запрос медленный,
  но не почему — для этого `EXPLAIN` руками.

## Структура

```
sql/         роль monitoring, обёртка над pg_stat_statements, проверка прав
probe/       пробер: время отклика + метрики, которых нет в экспортёре
prometheus/  конфиг, правила алертов, юнит-тесты правил
grafana/     дашборд для импорта
windows/     установщик под Windows
tools/       проверка совместимости метрик с версией экспортёров
```
