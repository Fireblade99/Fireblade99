# Мониторинг PostgreSQL

Дашборд и алерты поверх экспортёров, которые уже стоят на хосте БД.

## Проверенная конфигурация

| Что | Версия |
|---|---|
| PostgreSQL | 14.2 (RHEL) |
| postgres_exporter | 0.17.1, порт 9187, коллекторы по умолчанию |
| node_exporter | 9100, полный набор |
| Тома базы | `/data_db` (данные), `/mwal` (WAL), `/pg_log` (логи) |

Всё ниже проверено на живом стенде с этими версиями, а не по документации.

## Минимум: только дашборд

Ничего ставить и никого просить не нужно.

1. В Prometheus добавить две цели (см. `prometheus/prometheus.yml`).
   Метка `pg_instance` должна быть **одинаковой** в обеих — по ней
   дашборд связывает метрики базы и хоста.
2. Grafana → Dashboards → Import → загрузить
   `grafana/postgres-dashboard.json`.

Файлы правил для дашборда не нужны: все выражения внутри панелей.

**Точки монтирования зашиты** в панели про диски. Если PGDATA лежит не
на `/data_db`, поправить в трёх панелях. Фильтр намеренно узкий: иначе
`/boot` и `/var/log/audit` дают постоянный шум.

## Алерты

`prometheus/rules/*.yml` — 21 алерт и 7 recording rules, работают на
текущей конфигурации без доработок. Условия готовы, канал уведомлений
подключается отдельно (Alertmanager или Grafana Alerting).

Основное, что закрыто: недоступность базы, насыщение по коннектам,
зависшие `idle in transaction`, заполнение `/data_db` и `/mwal`
(включая предсказание за сутки), OOM killer, исчерпание файловых
дескрипторов, попадания в кэш, откаты, взаимоблокировки, временные
файлы, досрочные чекпоинты, отставание репликации, ошибки архивации.

### Набор для Grafana Alerting (рабочий)

`grafana/alerts-<группа>.yml` — то, что реально стоит в Grafana: 14
правил на группу хостов, у `prod-dp` 15 из-за разных порогов по долгим
транзакциям. Заливаются штатным импортом: Alerting -> Alert rules ->
New alert rule -> Import to Grafana-managed rules.

| Требование | Правило | На чём держится |
|---|---|---|
| доступность, `select 1` | `БазаНеОтвечает` | `pg_up` — экспортёр каждый скрейп выполняет запросы в базе |
| отказы в подключении | `СлотыПодключенийИсчерпаны` + `БазаНеОтвечает` | счётчика отказов в Postgres нет, ловится с двух сторон от стенки |
| коннекты > 80% | `СлотыПодключенийНаИсходе` | `pg_stat_activity_count / pg_settings_max_connections` |
| `idle in transaction` > 2 мин | `ЗависшаяIdleInTransaction` | `pg_stat_activity_max_tx_duration{state=~"idle in transaction.*"}` |
| CPU > 80% | `ЗагрузкаCPU` | `node_cpu_seconds_total{mode="idle"}` |
| рост latency | `ЗадержкаДискаЧтение`, `ЗадержкаДискаЗапись`, `МедленноеЧтениеБлоков` | среднее за окно, не перцентили — см. «Чего здесь нет» |
| диск > 80% | `ДискБазыКончается` | `node_filesystem_avail_bytes` по списку точек монтирования |
| блокировки | `СессииЖдутБлокировку`, `Взаимоблокировки` | порог по длительности ожидания, а не по количеству блокировок |
| долгие транзакции | `ДолгаяТранзакция` (+`Dbp2`) | `pg_stat_activity_max_tx_duration{state!~"idle.*"}` |
| отставание реплики > 60 с | `ОтставаниеРеплики` | `pg_replication_lag_seconds`, на мастере ноль по построению |
| — | `МониторингОслеп` | `up` — без него молчание остальных неотличимо от тишины |

Два места, где правило намеренно устроено не так, как просили:

* **Блокировки — порог по времени, а не по количеству.** Число
  блокировок ничего не значит: OLTP держит их сотнями, DWH под
  загрузкой тысячами. Разделяет длительность. `for: 2m` требует, чтобы
  сессия ждала чужую блокировку на КАЖДОМ вычислении внутри окна —
  один чистый скрейп сбрасывает отсчёт, и короткие ожидания отсеиваются
  сами. Тюнить в таком порядке: сначала `for` до 5m, потом порог с 0 до
  2-3 сессий.
* **Долгие транзакции разведены с `idle in transaction` по состоянию
  сессии.** Иначе одна зависшая транзакция даёт два уведомления. Здесь
  же разный диагноз: `idle in transaction` чинится в коде приложения,
  долгий `active` — планом и индексами.

Проверено юнит-тестами: `promtool test rules
prometheus/tests/alerts_prod_dp_test.yml`. Тесты держат разделение
порогов по хостам, отсутствие двойных срабатываний, сохранение метки
`pg_group` после агрегаций (без неё Grafana нечем разводить уведомления
по группам), изоляцию групп и молчание правил на простаивающем диске.

### Дополнительные наборы

`prometheus/rules/optional/` подключать **только** когда появятся нужные
метрики. Иначе правила молча никогда не сработают — худший вид поломки
мониторинга, потому что выглядит как «всё спокойно».

**`postgres.alerts-collectors.yml`** — 10 правил. Нужны флаги в
`ExecStart` экспортёра (рестарт Postgres НЕ требуется, только рестарт
самого экспортёра):

```
--collector.database_wraparound   --collector.postmaster
--collector.replication_slot      --collector.stat_statements
```

Даёт wraparound, рестарт базы, брошенные слоты и медленные запросы.

**`postgres.alerts-probe.yml`** — 11 правил. Нужен пробер
(`windows/Install-PgProbe.ps1`). Он даёт три вещи, которых нет ни у
одного коллектора:

* **время отклика**, разложенное на слои — сеть, TLS с авторизацией,
  запрос по новому соединению, запрос по готовому. По тому, какой слой
  вырос, видно, тормозит сеть, установка соединения или сам сервер;
* **«база жива, но недоступна отсюда»** — расхождение `pg_up` и
  `pgprobe_up` отличает сетевую аварию от отказа базы;
* заблокированные сессии — `pg_locks_count` разбит по `mode`, но не по
  `granted`, и коллектора для этого нет.

Экспортёр живёт на хосте БД и путь по сети не видит по определению,
поэтому пробер ставится рядом с Prometheus, а не рядом с базой.

## Перед тем как верить алертам

```bash
python3 tools/check_targets.py \
    --postgres-exporter http://<хост>:9187/metrics \
    --node-exporter     http://<хост>:9100/metrics
```

Вытаскивает из правил все метрики, на которые они ссылаются, и сверяет
с тем, что реально отдают эндпоинты. Отсутствующая метрика Prometheus
не роняет — правило просто никогда не срабатывает, и заметить это
можно только так.

## Известная проблема установки

**Экспортёр подключён к базе без пользовательских таблиц** (судя по
всему, к `postgres`). Проверено воспроизведением: при подключении к
пустой базе `pg_stat_user_tables_*` даёт ровно 0 серий.

Следствие: не собирается статистика по таблицам приложения — мёртвые
строки, давность вакуума, размеры, полные сканы вместо индексных.
Коллектор тут ни при чём, он включён по умолчанию.

Лечится сменой базы в строке подключения экспортёра либо
`--auto-discover-databases`. Панелей и алертов на эти метрики в базовом
наборе нет — их нечем наполнить.

## Чего здесь нет

* **Логов Postgres.** Лежат на `/pg_log`, но экспортёрами не читаются.
  Нужен отдельный сбор на хосте.
* **Надёжного алерта на слот, которым ни разу не пользовались** —
  метрика отдаёт для него `NaN` (проверено). Опасный случай (слот
  работал, потребитель умер) отслеживается; последствия любого варианта
  ловит алерт на `/mwal`.
* **Перцентилей задержки (p95/p99).** Ни node_exporter, ни
  postgres_exporter не отдают гистограмм по времени операций — только
  счётчики суммарного времени и количества операций. Из них считается
  среднее за окно, и ничего кроме среднего: хвост оно смазывает, полку
  видит. Что дало бы больше: `--collector.stat_statements` даёт
  `mean_exec_time` и `stddev` по каждому запросу отдельно (это, как
  правило, полезнее одной общей цифры), а настоящие перцентили —
  только инструментирование приложения либо статистика pgbouncer.
* **Разбора планов запросов.** Видно, какой запрос медленный, но не
  почему. Причём в метриках только `queryid` без текста — сам запрос
  придётся смотреть в `pg_stat_statements` руками.

## Проверка

```bash
promtool check rules prometheus/rules/*.yml prometheus/rules/optional/*.yml
promtool test rules prometheus/tests/base_test.yml
python3 probe/test_classify.py
```

Тесты проверяют и несрабатывание тоже: ложные срабатывания приводят к
тому, что алерты начинают игнорировать, а это хуже их отсутствия. Три
случая зафиксированы регрессиями, потому что каждый уже был ошибкой:

* фильтр дисков по точкам монтирования — общий фильтр орал бы на
  `/boot` и `/var/log/audit`;
* на **простаивающей** базе попадания в кэш не определены (`0/0`), а не
  равны нулю — иначе алерт «< 95%» будил бы каждую ночь;
* `last_autovacuum = 0` означает «никогда», а не 1970 год.

## Структура

```
grafana/     дашборд для импорта — самодостаточный
prometheus/  конфиг, базовые правила, optional/, тесты правил
tools/       сверка правил с реальными эндпоинтами
probe/       пробер времени отклика (опционально)
sql/         роль monitoring и обёртка pg_stat_statements (для пробера)
windows/     установщик пробера
```
